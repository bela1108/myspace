# DUO139

This linter looks for misused security check results when synchronous and
asynchronous check factories are mixed in the same package. Only the declared
set of check APIs (`verify_token`, `check_permission`, `is_authorized`) is
analyzed.

The linter uses local `async def` definitions, `await` usage, and limited
assignment/return relationships to distinguish proven checks from retained
asynchronous objects. A coroutine used as a condition is always truthy, so a
missing `await` silently disables the check. Three situations are reported:

* an async security check result used without `await`
* an awaited security check whose result is never used
* a check result that cannot be confirmed (external function or inconsistent
  branch results) and needs manual review

Note that a plain `await` of a non-check function never counts as a security
check.

## Problematic code

```python
async def verify_token(token):
    ...

async def handler(token):
    if verify_token(token):  # coroutine is always truthy
        grant_access()
```

```python
async def check_permission(user):
    ...

async def handler(user):
    await check_permission(user)  # result never used
    grant_access()
```

## Correct code

```python
async def is_authorized(user):
    ...

async def handler(user):
    allowed = await is_authorized(user)
    if allowed:
        grant_access()
```

## Rationale

When a security check factory is asynchronous, calling it produces a
coroutine rather than a decision. Using that coroutine as a condition, or
awaiting the check without acting on its result, gives the appearance of
validation while the protected action always runs.

## Exceptions

* Check APIs that are not defined locally (external functions) cannot be
  confirmed statically and are flagged for manual review instead.
* Assignments whose results differ across branches are also flagged for
  manual review.
