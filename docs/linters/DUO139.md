# DUO139

This linter searches for data-masking calls placed on an in-house scheduling
queue where the masking level (data classification) is selected inside the
deferred callback rather than being fixed when the job is registered. Because
the callback executes later, a loop variable or a rebound closure variable can
resolve to a different value than what a static reviewer reading the
registration site might assume.

The linter only reasons about source it can see. Each scheduling call is
analyzed in isolation, so captures from different queue batches are never
merged. Callback expressions that are not locally-defined functions, including
anything returned by an unknown higher-order wrapper, are flagged for manual
review rather than guessed at.

Three closure behaviors are modeled separately:

* `closure-read` - a free variable is read from an enclosing function scope;
  when it is assigned inside a loop body the late-binding value at execution
  time cannot be proven.
* `default-capture` - the level is read through a parameter whose default value
  is a literal, which is bound once at registration and is therefore provable.
* `nonlocal-reassignment` - a `nonlocal` variable is rebound inside the
  callback, so any level derived from it reflects execution-time state rather
  than the registration state.

## Problematic code

```python
import datamask

queue = datamask.Queue()

def clean(records, tier):
    def job():
        # tier is read from the closure at execution time; inside a loop this
        # is the classic late-binding problem.
        datamask.mask(records, level=tier)

    queue.submit(job)

for tier in ("public", "internal", "confidential"):
    clean(load_records(tier), tier)
```

## Correct code

Bind the level at registration time, either with a default argument or with a
literal captured directly:

```python
import datamask

queue = datamask.Queue()

def clean(records, tier):
    def job(level=tier):
        datamask.mask(records, level=level)

    queue.submit(job)

for tier in ("public", "internal", "confidential"):
    clean(load_records(tier), tier)
```

## Rationale

Data masking must apply the classification that was intended when the job was
queued. A level that depends on mutable closure state can silently change
before the deferred job runs, leading to under-masking of sensitive data.

## Exceptions

* Levels expressed directly as literals, or captured through literal-valued
default arguments, are provable at registration time and reported as such.
* Callbacks that are not locally-visible functions, including the result of an
unknown higher-order wrapper, cannot be analyzed from source alone. The
scheduling call is flagged for manual review with no provable level.
