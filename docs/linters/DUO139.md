# DUO139

This linter searches for security audit records that are written while the
surrounding database transaction may still be rolled back. An audit entry
written before the transaction boundary is a confirmed action even when the
transaction later undoes the underlying security change, leaving an audit
stream that describes an action which never took effect.

The set of relevant calls is declared explicitly per project through
`AuditTransactionConfig`:

* `audit_write_functions`: functions that append a confirmed security-action
  record to the audit stream.
* `post_commit_callbacks`: registrars that only invoke their callable argument
  after the transaction has committed (e.g. `transaction.on_commit`).
* `outside_transaction_adapters`: adapters that are only valid outside of a
  transaction; reaching one while a transaction is open is reported.
* `commit_functions` / `rollback_functions`: the transaction boundary calls.

Local wrapper functions are followed when their body resolves to a confident
ordering. When a call is dynamically bound, or a wrapper cannot be resolved
statically (including same-named wrappers without a unique lexical binding),
the linter reports an `unknown` result instead of guessing. Nested functions
keep their own transaction state; once a nested scope exits, the outer
transaction state decides whether the write is safe.

## Problematic code

```python
def log_disposition():
    log_security_event("user blocked")


def handler():
    log_disposition()
    transaction.rollback()
```

The wrapper succeeds on its own, but the outer transaction rolls back after the
call. The audit stream keeps a confirmed "user blocked" entry for an action
that was undone.

## Correct code

Register the audit write as a post-commit callback so it only runs once the
transaction has committed:

```python
def handler():
    def after_commit():
        log_security_event("user blocked")

    transaction.on_commit(after_commit)
    transaction.commit()
```

## Rationale

Audit records are only trustworthy when their lifecycle matches the lifecycle
of the action they describe. A record that survives a rollback breaks the
audit trail and can drive incorrect incident response, compliance reporting,
or automated remediation.

## Exceptions

* Writes intentionally sent to a system outside the transaction should use the
  configured outside-transaction adapters, and only when no transaction is open.
* Calls the linter cannot resolve statically are surfaced as `unknown` rather
  than silently ignored; review these bindings manually or restructure them so
  the target is a statically resolvable name.
